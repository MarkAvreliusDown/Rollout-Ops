# CLAUDE.md — Доска запуска ЦФ (cf_board)

Контекст для Claude Code при работе с этим проектом. Прочитай целиком перед
тем, как что-то менять — здесь жёсткие правила, которые нельзя нарушать.

## Что это

Локальный Django-сайт для управления запуском/реконструкцией/доп. работами
торговых точек по четырём филиалам (СЗФ, УФ, ПФ, ЦФ). Владелец —
не разработчик, менеджер по запуску торговых точек, работает с сайтом сам,
без команды. Никуда не деплоится — крутится на 127.0.0.1 (и в локальной сети)
на компьютере пользователя под Windows.

Пользователь коммуницирует по-русски. Объяснения — простым языком, без
непрошеного технического жаргона, по шагам, если что-то в консоли/установке.

## Технологии и запуск

- Python + Django 5, SQLite, чистый HTML/CSS/JS в шаблонах (без сборщиков,
  без React/Vue/Tailwind-компилятора)
- venv: `venv\Scripts\activate.bat`
- Запуск сайта: `start_server.bat` (в проекте) → слушает `0.0.0.0:8000`,
  доступен с других устройств в локальной сети
- Запуск Telegram-бота: `start_bot.bat`, **отдельное окно**, работает
  параллельно с сайтом (`python manage.py telegram_bot`, long polling)
- Оба .bat добавлены в автозагрузку Windows пользователем (`shell:startup`)
- pip: `pip install -r requirements.txt` (Django, Pillow, python-dotenv,
  requests, python-docx, beautifulsoup4, pypdf)
- `.env` в корне проекта (рядом с `manage.py`) — там все ключи и токены,
  в репозиторий/дампы не попадает никогда

### Переменные окружения (.env)

```
OLLAMA_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5:7b
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...        # можно несколько через запятую
SITE_PASSWORD=...           # пароль на весь сайт, пусто = защита выключена
```

### Бэкапы

`python manage.py backup` (или двойной клик по `backup.bat`) собирает
`db.sqlite3` + папку `media/` в один ZIP в `C:\mybacks\` (папка создаётся
сама). `.env` в архив намеренно не попадает. `setup_backup_task.bat` один
раз создаёт задание в Планировщике заданий Windows на ежедневный запуск
`backup_silent.bat` в 10:00 (тот же бэкап без окна с паузой).

## Модели (board/models.py)

- **Store** — магазин: branch (szf/uf/pf/cf), store_type
  (opening/reconstruction/extra/**closing** — «Закрытие» добавлено в 0030,
  ключ `opening` внутри остался прежним, хотя на экране подписан «Новые
  Магазины»), number, address, region, contact (старое текстовое поле,
  оставлено ради совместимости), notes, is_archived, contractors (JSON —
  подрядчики, выбранные при создании, используются для автозаполнения
  «Писем»), kso_count/cash_count/area_format/columns_count/columns_type/
  has_meat_scale/access_points_count (техданные объекта, тоже автозаполняют
  «Письма»), **kanban_status** (new/progress/review/open — стадия на
  канбане главной страницы, двигается вручную, не связана со статусом задач)
- **Task** — задача: store (FK), title, due_date, **due_time** (необязательно,
  конкретное время — см. ниже), status, order, parent (self-FK для подзадач),
  anchor_key/depends_on/offset_days (авторасчёт дат от опорных дат),
  icon_name/icon_color (ручной выбор иконки), notified_at (метка отправленного
  telegram-уведомления о сроке)
- **Report** — **один на магазин** (UI это соблюдает, но в БД FK не unique —
  исторические дубли не удалялись, см. раздел про отчёты ниже). final_text —
  редактируемый вручную текст, собирается из StoreLog кнопкой на сайте
- **ReportPhoto** — файлы к отчёту (поле `file`, FileField — любой тип, не
  только картинки, было переименовано из `image` в миграции 0006)
- **Note** — заметка. `task=null` → общая заметка (список на главной и на
  `/notes/`), `task=<Task>` → заметка привязана к конкретной задаче. Есть
  `due_date`/**`due_time`** (попадает в сегодня/завтра/просрочено, уведомления
  в Telegram работают так же, как у Task — см. ниже), `source` (web/tg),
  `is_archived` (архив заметок — `/notes/archive/`)
- **NoteFile** — файлы к заметке
- **Contact** — контакт магазина: name, role, phone, telegram, max_contact
- **Problem** — проблема по магазину (текст, is_resolved, когда решено) —
  в отличие от `Store.notes` (одно текстовое поле), можно вести несколько
  записей по времени и отмечать решённые/нерешённые
- **StoreLog** / **StoreLogFile** — журнал работ по объекту (дневник);
  попадает в контекст ИИ-чата; `source` = web/tg/report
- **TelegramSession** — состояние диалога с ботом на chat_id: выбранный
  store, mode (`log` — пишем в журнал объекта / `note` — быстрая заметка
  без магазина)
- **Article/ArticleImage/ArticleFile** — база знаний (импорт файлов, печать,
  экспорт в .docx/.txt, поиск с ИИ)
- **ChecklistItem** — чек-лист по магазину
- **SalarySettings/Bonus** — калькулятор зарплаты/премий
- **ReconstructionRecord/ReconstructionDocument** — история реконструкций
  с документами (для премий)
- **LetterCompany** — вкладка-компания в генераторе писем (`/letters/`):
  таблица графика работ (JSON columns/rows) + получатели; `page`
  (schedules/accounts) — на какой странице показывается; `is_store_contractor`
  — участвует в автозаполнении при создании магазина/появлении даты задачи
  (`sync_new_store_to_letters` / `_sync_task_date_to_letters` в models.py)
- **Contractor** — подрядчик для расчёта бюджета: прайс-лист по умолчанию
  (оборудование + виды работ, JSON), копируется в `BudgetCalculation` при
  создании расчёта
- **BudgetSettings** — общие настройки расчёта бюджета (ставка НДС),
  синглтон через `BudgetSettings.get()`
- **BudgetCalculation** — расчёт бюджета по объекту у выбранного подрядчика;
  оборудование/работы — рабочая копия прайса на момент создания, правки не
  трогают сам прайс подрядчика; суммы считает `compute_budget_totals()`

## ⚠️ Жёсткие правила — никогда не нарушать

1. **Никогда не предлагать удалить `db.sqlite3` или пересоздать миграции
   с нуля.** В базе много реальных рабочих данных (магазины, задачи,
   контакты, отчёты). Любое изменение моделей — **только через новую
   аддитивную миграцию** (AddField / CreateModel / RenameField). Уточнить
   у пользователя текущий номер миграции, если не указано явно —
   **на момент этого файла последняя миграция:
   `0030_rename_opening_to_new_stores`, следующая — `0031_...`**.
2. **Всегда присылать готовые файлы целиком** (create_file/present_files),
   не куски кода для ручной вставки — пользователь не разработчик и не
   будет сам склеивать патчи.
3. Меняются только шаблоны (.html) → перезапуск сервера не нужен.
   Меняются .py (models/views/urls/admin/management-команды) → нужен
   перезапуск `python manage.py runserver` (или `start_server.bat`).
4. Меняется `telegram_bot.py` → нужен перезапуск именно бота (отдельное
   окно/процесс от сайта, не перезапускается вместе с сайтом).
5. Перед изменением кода стоит попросить актуальный дамп проекта, если
   есть подозрение, что файлы могли разойтись с тем, что видел Claude
   раньше (`dump_source.bat` в корне — PowerShell, собирает все .py/.html/.bat
   в один текстовый файл, исключая venv/__pycache__/media/logs).

## Ключевые технические решения и грабли (уже отловлены — не наступать снова)

- **Настройки — `cf_board/settings.py`**, НЕ `board/settings.py`. Ранее была
  путаница из-за случайного дубля не в том месте — ключи из `.env` не
  подхватывались.
- `.env` лежит в корне проекта рядом с `manage.py`;
  `settings.py` грузит его через `load_dotenv(BASE_DIR / ".env")` с явным
  путём.
- ИИ работает только через локальную модель Ollama (`OLLAMA_URL`/
  `OLLAMA_MODEL` в `.env`, по умолчанию `http://127.0.0.1:11434` и
  `qwen2.5:7b`) — используется и в ИИ-чате на дашборде, и в поиске по базе
  знаний. Ничего не уходит в интернет: раньше был выбор между облачным
  Gemini и Ollama через `LLM_PROVIDER`, но Gemini убран полностью, чтобы
  данные компании не покидали компьютер (риск NDA) — см. git-историю при
  необходимости. Для работы ИИ-функций на компьютере должно быть
  установлено и запущено приложение Ollama с нужной моделью.
- Лимит символов контекста для ИИ-чата — 12 000 (ограничение видеопамяти/
  `num_ctx` локальной модели).
- **`<input type="date">` не должен сабмитить форму по `onchange`** — при
  ручном наборе даты с клавиатуры форма отправляется на середине ввода и
  выкидывает из поля. Дата подтверждается отдельной кнопкой «✓».
- **CSRF на fetch-запросах**: там, где не обычная Django-форма (ИИ-чат на
  дашборде), токен достаётся через `getCookie('csrftoken')`.
- **Windows + кириллица в .bat**: сохранять в `cp866` БЕЗ BOM, иначе `chcp`
  ломается и Python не находится. UTF-8 с BOM тестировался — не работает.
- **Django admin migrations**: старые Report у некоторых магазинов
  дублировались (несколько черновиков на один магазин из старого workflow) —
  это ожидаемо, они не удалялись (см. `reports_to_log`), просто на странице
  магазина показывается только последний по дате.

## Как устроены основные механики

### Задачи и авторасчёт дат (только «Открытие»)

При создании магазина в разделе «Открытие» автосоздаётся 14 задач из
`OPENING_TASK_TEMPLATE` (views.py). Две опорные (`anchor_key`): **Открытие**
и **ВПК-2** — дату вводит пользователь. Остальные считаются через
`depends_on` + `offset_days`, пересчёт — в `recalc_dependents()` при
сохранении даты опорной задачи. Реконструкция и Доп. работы создаются
**без** автошаблона (если понадобится — заводить свой TEMPLATE по аналогии).

### Время у задачи и заметки (due_time)

Необязательное поле рядом с датой — есть и у `Task`, и у `Note` (0028).
Пусто — работает как раньше (только по дате). Если задано — показывается
значком 🕐 и **бот раз в ~30 секунд проверяет и присылает уведомление в
Telegram**, когда время наступает (`check_due_tasks()` в `telegram_bot.py`,
работает только пока бот запущен). При любом изменении due_date/due_time
поле `notified_at` сбрасывается, чтобы уведомление могло прийти заново на
новый срок.

### Иконки задач (icons.py + templatetags/board_extras.py)

Иконка подбирается автоматически по ключевым словам в названии задачи
(`ICON_RULES` в `icons.py`, набор иконок — Tabler Icons через CDN). Можно
выбрать вручную через пикер в форме создания задачи или в блоке «иконка» у
существующей задачи (`Task.icon_name`/`icon_color`, пусто = автоподбор).
Тег `{% task_icon_badge t %}` принимает **объект задачи**, не строку (важно
при добавлении новых мест вывода — передавать `t`, а не `t.title`).

### Отчёт (Report) — один на магазин

Кнопка «🧩 Собрать отчёт из журнала» склеивает записи `StoreLog` по датам в
редактируемый текст (`final_text`). Никакого ИИ в отчёте больше нет
(убрано по просьбе пользователя — раньше была отдельная кнопка
«Оптимизировать с ИИ»). «Пересобрать» — перезатирает текст свежими записями
журнала (спрашивает подтверждение). В БД может быть больше одного Report на
магазин исторически — UI показывает только последний, старые не трогать.

### Journal / StoreLog

Дневник работ по объекту. Попадает в контекст ИИ-чата на дашборде (до 40
записей на магазин). Заполняется вручную на сайте и через Telegram-бота
(режим «журнал»).

### Telegram-бот (board/management/commands/telegram_bot.py)

Long polling (не webhook — нет белого IP). Два режима сессии
(`TelegramSession.mode`):

- **`log`** (по умолчанию) — выбрали филиал → тип → объект (инлайн-кнопки,
  пагинация по 12), дальше всё уходит в `StoreLog` этого объекта.
- **`note`** — быстрая заметка/задача без привязки к магазину → создаётся
  общий `Note` (виден на главной сайта). Включается кнопкой «💭 Заметка» или
  командой `/zametka`, держится, пока не выбран объект (это автоматически
  возвращает в режим `log`).

Внизу экрана — **постоянная клавиатура** (`ReplyKeyboardMarkup`,
`resize_keyboard`/`is_persistent`) с кнопками «✍️ Журнал / 💭 Заметка /
📅 Сегодня / 📍 Где я» — не нужно печатать команды. Slash-команды (`/start`,
`/objekt`, `/zametka`, `/gde`, `/segodnya`) продолжают работать параллельно.

**Альбомы (несколько вложений одним сообщением)** — Telegram шлёт их как
несколько апдейтов с общим `media_group_id`. Бот копит части в
`_pending_groups` и собирает в одну запись, если новых частей не было
`MEDIA_GROUP_WAIT` (2) секунд — реализовано через динамический
`poll_timeout` в цикле `getUpdates` (короче, если есть незакрытый альбом).

Доступ — только chat_id из `TELEGRAM_CHAT_ID` (через запятую, можно
несколько — уведомления о сроке уходят всем).

### Защита паролем (board/middleware.py)

`SitePasswordMiddleware` — если `SITE_PASSWORD` в `.env` пуст, сайт открыт
как раньше (без пароля). Если задан — любой запрос без флага
`site_authenticated` в сессии редиректит на `/login/`. Один общий пароль,
без пользователей/логинов, сессия хранится в браузере (у каждого
устройства/браузера — свой вход). Telegram-бот эту защиту не видит —
работает напрямую через ORM, не через HTTP.

### Доступ по локальной сети

`ALLOWED_HOSTS = ["*"]`, сервер слушает `0.0.0.0:8000`
(`start_server.bat`). С другого устройства — `http://<IP-компьютера>:8000`
в той же Wi-Fi-сети (IP смотрится через `ipconfig`). Из-за этого пароль
(см. выше) особенно важен — без него сайт открыт всем в сети.

### Дизайн / мобильная адаптация

- Тёмная/светлая тема — `data-theme="dark"` на `<html>`, CSS-переменные,
  выбор в localStorage, применяется до отрисовки (инлайн-скрипт в `<head>`).
- Фон — не ровный, лёгкий градиент из `--accent`/`--accent2` через
  `radial-gradient` + `color-mix()` (нужен современный браузер, деградирует
  тихо на старых).
- **Desktop/iPad (>860px)** — обычный сайдбар слева, без изменений.
- **Mobile (≤860px)** — сайдбар превращается в выезжающую панель
  (`position: fixed`, `transform: translateX(-100%)`, класс `.open`),
  открывается гамбургером в компактной шапке (`.mobile-topbar`), закрывается
  по тапу на фон-подложку или на любую ссылку внутри меню. Старый вариант
  (сжатое горизонтальное меню в строку) — не использовать, специально
  заменён на off-canvas, потому что не помещается при таком числе разделов.
- Списки/плитки — переключатель хранится в localStorage под двумя разными
  ключами независимо: `tasksView` (страница магазина) и `dashView`
  (дашборд).
- Архив: `Store.is_archived`, фильтр `?archived=1` в query-string,
  архивные магазины исключены из запросов дашборда.

## Работа через субагентов (обязательно)

В проекте настроены специализированные субагенты (`.claude/agents/`):
`analyst`, `product-manager`, `designer`, `backend-developer`,
`web-developer`, `reviewer`, `tester` — и отдельно `docs-sync`, который
**пользователь вызывает сам вручную**, Claude не должен вызывать его
самостоятельно.

Для всех задач, кроме мелких (правка опечатки, ответ на вопрос без
изменения кода), Claude должен пользоваться остальными субагентами
проактивно, а не делать всё в основном потоке. Типовой порядок для
нетривиальной задачи:

1. **`analyst`** — если запрос пользователя неоднозначен, затрагивает
   несколько частей системы (модели/бот/шаблоны) или нужно сначала понять,
   как что-то устроено сейчас.
2. **`product-manager`** — если пользователь предлагает новую фичу или
   крупное изменение и нужно решить, что именно делать и в каком порядке,
   с учётом уже известных компромиссов проекта.
3. **`designer`** — если задача затрагивает внешний вид/раскладку/UX
   (новый экран, блок, компоновка на mobile/desktop) — до того, как
   `web-developer` начнёт вёрстку, чтобы решение было в рамках уже принятой
   визуальной системы проекта.
4. **`backend-developer`** — для изменений в `board/models.py`,
   `views.py`, `admin.py`, `telegram_bot.py`, `management/commands/`,
   `cf_board/settings.py` (миграции, серверная логика, интеграция с
   локальной Ollama).
5. **`web-developer`** — для изменений в `board/templates/board/` и
   `board/templatetags/board_extras.py` (HTML/CSS/JS, тема, мобильная
   адаптация).
6. **`reviewer`** — обязательно вызывать после любых правок кода в
   `board/` или `cf_board/`, **до того как** отчитаться пользователю о
   завершении задачи. Проверяет соответствие правилам этого файла
   (аддитивные миграции, безопасность, целые файлы, уже отловленные
   грабли).
7. **`tester`** — обязательно вызывать после правок в
   `board/views.py`, `models.py`, `telegram_bot.py` или шаблонах, чтобы
   убедиться, что ничего не сломалось (создание магазина/задач/отчётов,
   работа бота и т.д.).

Не пропускать `reviewer` и `tester` «ради скорости» — это единственная
защита от того, чтобы сломать боевую базу и рабочие сценарии пользователя,
который сам код не проверяет. `docs-sync` в эту цепочку не входит — его
запускает пользователь, когда сочтёт нужным.

## Стиль работы с пользователем

- Общаться по-русски, простым языком, без непрошеного технического жаргона
- Объяснять по шагам, что куда вставить/нажать — пользователь не
  разработчик
- Присылать файлы целиком, не диффы/патчи
- Перед изменением моделей — уточнять текущий номер последней миграции,
  если не очевиден
- Не предлагать разрушительные операции с БД ни при каких обстоятельствах
